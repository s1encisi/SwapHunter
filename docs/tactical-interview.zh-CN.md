# 项目讲述与面试证据

讲述使用当前工程事实，实测结果只引用[本轮验证记录](tactical-validation.zh-CN.md)对应构建。下面是可修改的口述稿，不代表已经完成真人体验或取得性能提升。

主要求职方向：Unity/C# 游戏客户端与玩法系统；邻近方向是实时交互、仿真或游戏工具开发。本项目不作为线上后端或分布式服务经验。

## 30秒

> 《换位猎手》是一个围绕双向换位设计的Unity单机FPS。我主导玩法需求、规则取舍和迭代决策，使用AI生成代码并辅助验证。当前把四职业、八项职业技能、共享商店和关卡成长接成一个完整流程。我重点能讲的是：如何把拥有、职业资格和配装分开，以及用出发快照与幂等结算保证重试、退出和成功时资产一致。

## 2分钟

> 项目的核心操作是Q交换玩家与目标的位置，保留双方朝向，手雷等危险继续存在于原来的世界位置。因此玩法重点是站位和时机，而不只是伤害数值。我围绕这个方向确定了四职业、每职业两项技能、一项通用技能和双枪配装，并保留十二章不同任务入口。
>
> 成长系统的难点是把账户资产与一次行动分开。武器和技能全档拥有，但每职业有自己的合法配装；商品上架不等于已经拥有。采购先保存，再冻结出发快照，关内仅记录实际使用。死亡重试恢复快照，退出保留采购，成功才把三种道具实耗、奖励和首通一次提交。重复请求、重复结算和写失败都有明确处理。
>
> 我没有把全功能演示档当成普通成长证据。演示和QA使用隔离存储，经济路径用实际交易API逐章验证；技能专项、真实行走夹具和画面检查各自说明能证明什么。最终结果按构建身份引用，不把旧版本报告套到新代码上。
>
> 贡献上，需求和授权决策由我主导，代码及部分验证工具由AI生成、我推动迭代；新增环境模型和特效来自有明确许可的CC0资产。我会现场指向数据入口和关键调用，区分自己已经理解、能修改的部分与仍需进一步掌握的实现。

## 深入展开的顺序

先用一个具体场景讲规则：例如拿数据后还能留下普通敌人撤离，或换位后手雷仍在原地。再沿“整备→采购→快照→战斗→死亡/退出/成功”讲状态变化。随后只挑一个失效案例深入：重复采购、保存失败、Q终检失败或错误读取旧档。最后给对应源码和同构建证据，说明验证范围。控制开篇，不把全部技能数值逐条背出来。

## 八个项目追问

| 追问 | 回答应落到的事实 / 证据入口 |
|---|---|
| 1. 换位为何不是一次普通传送？如何处理失败？ | 双端空间合法性、预备后终检、双方朝向与世界危险；看PlayerMotor中的RequestSwap/换位流程与CoreV06QA，不只展示剪辑。 |
| 2. 已拥有的枪为什么还可能不能装备？ | 共享拥有与ClassCanUseWeapon分离，四份ClassLoadout独立；看TacticalPrototypeRules、ExpeditionStore.CanEquip/Equip。 |
| 3. 点两次购买或结算会不会重复扣钱？ | 相同requestId重试不重复执行；两次明确购买道具是两笔合法交易。requestId绑定商品和数量，runId绑定唯一回执；副本Persist成功才换内存；看ExpeditionData的Purchase/Commit/Settle和TacticalStorageChecks。 |
| 4. 死亡返还补给为何不撤销购物？ | 快照建立在采购之后；重试同runId，成功按实际消耗一次扣库存；看TacticalDeployment、ExpeditionRun和三道具夹具。 |
| 5. 技能会不会绕过原来的射击或空间规则？ | 扫描不赋予穿墙Q；精确按下一发实际枪弹消耗；快速装填缩短剩余时间而不造弹；看PlayerClassSkill、ClassSkillEffects、PlayerMotor与TacticalSkillChecks。 |
| 6. 如何说明不刷关也能成长？ | 给四职业逐章合法采购表和生成的economy-paths.json；固定每后续章65补给、无可选收益。它证明账面可行，不证明所有玩家都能实战过关。 |
| 7. 旧档升级怎样避免吞资产或重复补偿？ | 明确副本输入、未知S/D/r不补0、v5原值映射、纯候选生成和historical回执；看TacticalMigrationPreview及preview_tactical_migration.py。 |
| 8. 哪些是你的工作、AI工作和第三方工作？ | 说明需求/规则/授权决策、AI代码与验证协助、实际CC0模型/纹理及自有资产绑定；看THIRD_PARTY_ASSETS、D11SceneVisuals、作者生成工具和构建/包清单，不把第三方动画候选说成已接入。 |
